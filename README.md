# fab-anomaly-detector

Early-warning anomaly detection for semiconductor manufacturing sensor data. Applies time-series and unsupervised methods to multivariate process signals to surface likely defects before wafers move down the line.

> **Status:** early development. The data pipeline, detectors and benchmarks are being built in the open. See the [Roadmap](#roadmap).

---

## Why this exists

Making a chip takes hundreds of process steps, and each step is monitored by many sensors (temperature, pressure, gas flow, power, vibration and more). A small drift in one step can ruin a whole batch of wafers, but the problem may only be discovered at final testing, days or weeks later. By then, a lot of money and time has been wasted.

Detecting problems early is hard:

- **Hundreds of signals** change together, so watching each one alone misses combined shifts.
- **Defects are rare,** and labels often arrive late or are missing.
- **Normal conditions change** as equipment ages, is cleaned or is recalibrated, which causes false alarms.
- **Real fab data is confidential,** so students and researchers have little to practise on, and results are hard to compare.

`fab-anomaly-detector` aims to provide an open, reproducible starting point:

- **Unified loaders** for public semiconductor manufacturing datasets.
- **Several detection methods** under one interface, from classic statistical process control to modern machine learning.
- **Evaluation that reflects fab reality:** rare defects, late labels, drift over time.
- **Alarm-focused metrics:** detection lead time, false alarm rate and missed defects.
- **One command** to reproduce every reported result.

---

## What it detects

| Output | Meaning |
|---|---|
| **Anomaly score** | How unusual a wafer, lot or process run looks compared with normal behaviour |
| **Alarm** | A decision that something needs attention, raised only when the evidence is strong enough |
| **Contributing signals** | Which sensors or process steps contributed most to the anomaly |
| **Drift warning** | A slow shift away from normal that may not yet trigger a defect |

## Data

Real fab data is rarely public, so the project plans to use:

- **SECOM dataset (UCI Machine Learning Repository):** sensor measurements from a semiconductor manufacturing process with pass/fail labels
- **WM-811K wafer map dataset:** wafer map images with defect pattern labels, for experiments on spatial defect patterns
- **Synthetic process data** generated by this project, with injected drift and faults of known type and time, so detectors can be tested against known ground truth

Datasets are **not** redistributed in this repository. Scripts download them from the original sources, and each dataset keeps its own license and citation requirements.

Note that public datasets are small and old compared with modern fabs, so they are best used for method comparison, not for claims about real production performance.

## Planned approach

### Detection methods compared

- **Statistical process control:** control charts, EWMA and CUSUM on individual signals
- **Multivariate statistics:** PCA with T-squared and Q (SPE) statistics, a standard approach for process monitoring
- **Classical ML:** Isolation Forest, One-Class SVM, Local Outlier Factor
- **Deep learning:** autoencoders and sequence models for time series
- **Supervised baseline:** gradient boosting on labelled pass/fail data, for comparison with unsupervised methods

### Handling real-world issues

- **Missing values** common in sensor data
- **Feature selection** to remove sensors that carry no useful signal
- **Drift handling,** such as retraining windows and adaptive thresholds

### Metrics

- **Precision, recall and PR-AUC** (better than accuracy for rare defects)
- **False alarm rate:** alarms on good wafers or lots
- **Detection lead time:** how early the alarm comes before the defect is confirmed
- **Stability over time:** does the detector keep working as the process drifts?
- **Explanation quality:** on synthetic data, do the top contributing signals match the injected fault?

## How it works

```
multivariate sensor data (per wafer / lot / time window)
                    |
                    v
        cleaning + missing value handling + scaling
                    |
                    v
           feature extraction + selection
                    |
                    v
   time-aware split (train on earlier data, test on later)
                    |
                    v
   detector (SPC / PCA / ML / deep learning) -> anomaly score
                    |
                    v
   alarm threshold + contributing signals + drift warning
```

## Quickstart (planned)

```bash
git clone https://github.com/amoltathesoftwareengineer/fab-anomaly-detector.git
cd fab-anomaly-detector
pip install -r requirements.txt

# download and prepare a dataset
python -m fab_anomaly.datasets.download --name secom

# run a detector and print metrics
python -m fab_anomaly.run --detector pca --dataset secom

# reproduce the benchmark table
python -m benchmarks.run_all
```

## Limitations and responsible use

- Public datasets are small and may not represent modern manufacturing. Results here do **not** predict performance in a real fab.
- Real deployments need engineers who know the process. A flagged anomaly is a reason to investigate, not proof of a defect.
- Models trained on one tool or process may not work on another. Retrain and validate on your own data.
- This project is not affiliated with any semiconductor company. It is for research and education, and not a certified process control product.
